# Архитектура AI-агента для управления Chrome

## Обзор

AI-агент для автономного управления видимым Chrome-браузером на Windows. Агент использует LLM (OpenAI) для планирования и принятия решений, Playwright для управления браузером, и структурированную память для контекста.

## Выбор технологий

### Playwright for Go
- **Почему**: Нативный контроль браузеров, поддержка persistent context (профили), стабильность, API для скриншотов
- **Альтернативы**: Selenium (медленнее, менее стабильно), Chrome DevTools Protocol напрямую (сложнее)
- **Использование**: `LaunchPersistentContext` с `headless=false` и `PROFILE_DIR`

### OpenAI Go SDK (go-openai)
- **Почему**: Официальная поддержка function/tool calling, Vision API для скриншотов, структурированные ответы
- **Использование**: GPT-4o-mini или GPT-4o для Planner/DOM-Analyst/Critic с tool calling и vision-анализом
- **Модель**: По умолчанию `gpt-4o-mini` (более дешевая версия с теми же vision capabilities)

### Простой REPL
- **Почему**: Простая реализация через bufio.Scanner, достаточная для MVP
- **Использование**: Интерактивный REPL с командами (task, status, pause, resume, approve, deny, mode, help, quit)

### Zap (go.uber.org/zap)
- **Почему**: Высокая производительность, структурированное логирование, уровни
- **Использование**: JSON логи в `./runs/<timestamp>/run.log`, консольный вывод (human-readable)

### Godotenv + Viper
- **Почему**: Простая загрузка .env, валидация конфигов, типизированные структуры
- **Альтернативы**: envconfig (проще, но менее гибко)

### Cenkalti/backoff
- **Почему**: Экспоненциальный backoff для LLM и браузерных операций, ретраи с контекстом

## Dataflow

### 1. Инициализация
```
User Input → REPL → App.Init() → Agent.Start()
```

### 2. Основной цикл
```
1. User: task "найди товар X на Ozon"
2. Agent → Planner: "что нужно сделать?"
3. Planner → JSON plan
4. Agent → executeNextStep:
   a. Observe (если нужно) → PageState
   b. Screenshot (для click/type)
   c. executeTool:
      - Vision handler (для click/type с screenshot) → Analyst.FindClickCoordinates → DOM validation → ClickAt/TypeAt
      - или обычный executor → Browser
   d. Progress check (после click/type/navigate/scroll)
   e. Memory: сохранить шаг
5. Agent → Critic (каждые N шагов): "всё ок?"
6. Repeat until goal or error
```

### 3. Memory Levels

```
EPHEMERAL (3 последних шага)
    ↓ (суммаризация)
WORKING SUMMARY (≤1500 символов)
    ↓ (извлечение фактов)
FACTS (JSON структура)
```

### 4. Tool Calling Flow

```
LLM → ToolCall JSON
    ↓ (валидация схемы)
Tool Registry → executeTool
    ↓ (для click/type с screenshot)
Vision Handler → Analyst.FindClickCoordinates
    ↓
DOM Validation → ClickAt/TypeAt или fallback
    ↓ (security check)
Security Layer → approve/deny
    ↓ (execution)
Browser → Result → Memory
```

## Subagents

### Planner
- **Роль**: Разбивает задачу на шаги
- **Вход**: Task description, current state, memory
- **Выход**: JSON plan с шагами
- **Вызывается**: При старте задачи, при блокировке

### DOM-Analyst
- **Роль**: Анализирует DOM и скриншоты, определяет координаты для клика
- **Вход**: Screenshot, target description, page context
- **Выход**: ClickCoordinates (x, y, element_text) или PageState (elements, overlays, text_digest)
- **Вызывается**: Для vision-анализа (FindClickCoordinates), для проверки прогресса (CheckProgress), для анализа страницы (AnalyzePage)

### Critic
- **Роль**: Проверяет прогресс, выявляет ошибки
- **Вход**: History, current state, plan
- **Выход**: JSON с оценкой и рекомендациями
- **Вызывается**: Каждые 5 шагов, при ошибках

## Security Layer

Security Layer автоматически перехватывает опасные действия и запрашивает подтверждение через REPL.

### Опасные действия

Агент определяет опасные действия по следующим признакам:
- **Оплата**: text содержит "оплата", "payment", "купить", "buy", "purchase"
- **Отправка формы**: tool = "click" и target содержит "submit" или description содержит "отправить"
- **Удаление**: text содержит "delete", "удалить", "удаление"
- **Заказ**: text содержит "order", "оформить заказ", "заказать"
- **Отклик**: text содержит "apply", "отклик", "откликнуться"

### Механизм работы

1. **Intercept**: Security Layer перехватывает все tool calls перед выполнением
2. **Check rules**: Проверяет описание шага, target и args на наличие опасных паттернов
3. **REPL approval**: Если действие опасно, агент переходит в состояние `waiting_approval`
4. **User decision**: Пользователь может одобрить (`approve`) или отклонить (`deny`) действие
5. **Continue/Abort**: При одобрении действие выполняется, при отклонении - пропускается

### Dry Run режим

В режиме `dryrun` все действия логируются, но не выполняются. Это позволяет:
- Проверить план перед реальным выполнением
- Увидеть, какие действия будут выполнены
- Обнаружить потенциально опасные действия без риска

## Error Handling

1. **Ретраи**: Экспоненциальный backoff для LLM/network, до 5 попыток на шаг
2. **Recovery**: Planner обновляет план при ошибках → новый план
3. **Rollback**: При превышении лимита попыток → откат на предыдущий шаг
4. **Fallback**: Если vision не находит элемент → fallback на selector-based executor

### Детали Fallback механизма

Fallback происходит в следующих случаях:

1. **Vision-анализ не нашёл элемент**:
   - `FindClickCoordinates` вернул `found: false`
   - Причина указывается в `reason` (например, "элемент не виден", "нужно проскроллить")

2. **Координаты вне viewport**:
   - Координаты (x, y) находятся за пределами видимой области
   - Viewport check не проходит

3. **DOM-валидация не прошла**:
   - Элемент в точке (x, y) не соответствует target
   - Scoring элементов показал низкую уверенность

4. **Vision-based действие не выполнилось**:
   - `ClickAt` или `TypeAt` вернули ошибку
   - Браузер не смог выполнить действие по координатам

**Процесс fallback:**

```
Vision handler → Не удалось
    ↓
Возврат (done=false, err=nil)
    ↓
Agent → executeTool продолжает
    ↓
Selector-based executor:
  - Использует target (role, name, placeholder, text_contains)
  - Строит Playwright locator
  - Ищет элемент через Playwright API
  - Выполняет действие
```

**Преимущества fallback:**
- Надёжность: если vision не работает, используется проверенный метод
- Гибкость: автоматический выбор лучшего метода
- Устойчивость: агент продолжает работу даже при проблемах с vision
5. **Progress Check**: После важных действий проверяется прогресс через vision-анализ
6. **Timeout**: Context с таймаутами на все операции

## Persistent Profile

- `PROFILE_DIR` (env): путь к user-data-dir
- Playwright `LaunchPersistentContext` с этим путём
- Cookies, localStorage сохраняются между запусками
- Пользователь логинится один раз вручную

## Структура памяти

Агент использует трёхуровневую систему памяти для эффективного управления контекстом:

### EPHEMERAL
```go
type EphemeralMemory struct {
    Steps []Step // последние 3 шага
}
```
- **Назначение**: Хранит последние 3 шага для быстрого доступа к недавнему контексту
- **Использование**: Передаётся в Planner и Critic для понимания текущего состояния
- **Обновление**: Автоматически обновляется после каждого шага

### WORKING SUMMARY
```go
type WorkingSummary struct {
    Content string // ≤1500 символов
    UpdatedAt time.Time
}
```
- **Назначение**: Суммаризированное описание текущего прогресса задачи
- **Использование**: Передаётся в LLM для экономии токенов и фокуса на важном
- **Обновление**: Обновляется через LLM при необходимости, ограничен 1500 символами

### FACTS
```go
type Facts struct {
    URL string
    Goal string
    CompletedSteps []string
    Blockers []string
    Metadata map[string]interface{}
}
```
- **Назначение**: Структурированные факты о задаче и её выполнении
- **Использование**: Используется для долгосрочного контекста и анализа
- **Обновление**: Извлекается из Working Summary через LLM

### Управление памятью

- **Truncation**: PageState автоматически обрезается для экономии токенов
- **Summarization**: Working Summary обновляется при превышении лимита
- **Extraction**: Facts извлекаются из Working Summary для структурированного хранения

## Логирование и трассировка

- **Консоль**: Human-readable, уровни (debug/info/warn/error), zap
- **Файл**: `./runs/<timestamp>/run.log` (JSON, zap)
- **Trace**: `./runs/<timestamp>/trace.json` (tool calls, LLM requests)
- **Screenshots**: `./runs/<timestamp>/screens/step-XXX.png` (на каждом шаге для click/type)

### Структура логов

**run.log** содержит записи в формате JSON с полями:
- `timestamp` - время события
- `level` - уровень (debug, info, warn, error)
- `msg` - сообщение
- `module` - модуль (agent, browser, llm, subagents, etc.)
- Дополнительные поля в зависимости от события

**trace.json** содержит:
- `timestamp` - время запроса
- `type` - тип (llm_request, tool_call, vision_analysis)
- `request` - запрос (prompt, tool name, args)
- `response` - ответ (LLM response, tool result)
- `duration` - длительность операции

**Скриншоты:**
- `step-{N}.png` - скриншот перед действием (для vision-анализа click/type)
- `step-{N}-result.png` - скриншот после действия (для progress check)

### Анализ логов для отладки

1. **Поиск ошибок**: `jq 'select(.level == "error")' run.log`
2. **Анализ шагов**: `jq 'select(.module == "agent")' run.log`
3. **LLM запросы**: `jq 'select(.type == "llm_request")' trace.json`
4. **Vision анализ**: `jq 'select(.type == "vision_analysis")' trace.json`
5. **Progress checks**: `jq 'select(.msg | contains("Progress check"))' run.log`
6. **Plan updates**: `jq 'select(.msg | contains("Plan updated"))' run.log`

### Dry Run режим

Dry run режим позволяет проверить план без реального выполнения действий:

- Все действия логируются, но не выполняются
- Скриншоты создаются для vision-анализа
- LLM запросы выполняются (для планирования и анализа)
- Браузерные действия не выполняются (click, type, navigate не изменяют страницу)

Использование:
```
agent> mode dryrun
agent> task найти товар на Ozon
```

Это полезно для:
- Проверки плана перед реальным выполнением
- Отладки логики планирования
- Понимания, какие действия будут выполнены

## Расширяемость

- Новые tools: добавить в `internal/tools` (ToolRegistry, Executor)
- Новые subagents: интерфейсы `PlannerInterface`, `AnalystInterface`, `CriticInterface` в `internal/subagents/interfaces.go`
- Новые security rules: `internal/security/rules.go`
- Новые LLM providers: интерфейс `LLMClient` в `internal/llm`
- Vision strategies: можно заменить `VisionActionHandler` на другую реализацию
- DOM validation: можно заменить `Validator` на другую реализацию (через интерфейс `Evaluator`)

## Модульная архитектура

После рефакторинга код разделён на чёткие модули:

- **`internal/domvalidation`**: DOM-валидация координат vision-анализа
- **`internal/navigation`**: Разрешение URL для навигации
- **`internal/vision`**: VisionActionHandler для обработки click/type через vision
- **`internal/subagents`**: Интерфейсы и реализации Planner, Analyst, Critic
- **`internal/agent`**: AgentOptions, AgentController интерфейс

## Vision-анализ и DOM-валидация

### Vision-анализ для click/type

1. **Скриншот**: Перед click/type действием создаётся скриншот страницы
2. **LLM-анализ**: Analyst.FindClickCoordinates анализирует скриншот и определяет координаты (x, y) элемента
3. **Viewport check**: Проверяется, что координаты находятся в пределах видимой области
4. **DOM-валидация**: Validator проверяет элемент в DOM по координатам, сравнивает с target и element_text от LLM
5. **Выполнение**: Если валидация успешна, выполняется ClickAt/TypeAt, иначе fallback на selector-based поиск

### DOM-валидация

DOM-валидация использует JavaScript для:
- Получения элемента в точке (x, y) через `document.elementFromPoint`
- Обхода родительских элементов для поиска интерактивных элементов
- Проверки соответствия target (role, name, placeholder, text_contains)
- Сравнения текста элемента с `element_text` от LLM
- Scoring элементов для выбора наиболее подходящего

### Progress Check

После важных действий (click, type, navigate, scroll) выполняется проверка прогресса:

1. **Условие**: Progress check выполняется после click/type/navigate, и после scroll только если следующий шаг - observe/click/type
2. **Скриншот**: Создаётся скриншот текущего состояния страницы
3. **LLM-анализ**: Analyst.CheckProgress анализирует скриншот и определяет:
   - Достигнут ли ожидаемый результат
   - Что произошло на странице
   - Какое действие нужно выполнить дальше
4. **Адаптация плана**: Если прогресс не соответствует ожиданиям, Planner обновляет план

## Алгоритм самопроверки и адаптации плана

Агент использует многоуровневую систему самопроверки для обнаружения проблем и адаптации плана в реальном времени.

### Архитектура самопроверки

Система состоит из трёх уровней проверки:

1. **Progress Check** - проверка после каждого важного действия (реактивная)
2. **Critic Check** - периодическая проверка каждые N шагов (проактивная)
3. **Error Recovery** - проверка при ошибках выполнения (реактивная)

### Уровень 1: Progress Check (после каждого действия)

**Триггеры:**
- После `click`, `type`, `navigate`
- После `scroll` (только если следующий шаг - `observe`, `click` или `type`)

**Алгоритм:**

```
1. Выполнение действия (click/type/navigate/scroll)
   ↓
2. Ожидание 200ms для стабилизации страницы
   ↓
3. Создание скриншота текущего состояния
   ↓
4. LLM-анализ скриншота (Analyst.CheckProgress):
   - Сравнение ожидаемого результата с фактическим
   - Определение, что произошло на странице
   - Оценка применимости следующего шага плана
   ↓
5. Если progress_ok = false:
   - Формирование сообщения об отклонении
   - Вызов Planner.UpdatePlan с контекстом ошибки
   - Обновление текущего плана
   - Продолжение выполнения с обновлённым планом
```

**Пример сценария:**

```
План: "Найти поле поиска → Ввести текст → Нажать кнопку поиска"
Действие: Ввод текста выполнен
Progress Check: LLM видит, что текст введён, но кнопка поиска не видна (нужно проскроллить)
Результат: План обновлён: "Найти поле поиска → Ввести текст → Проскроллить → Нажать кнопку поиска"
```

### Уровень 2: Critic Check (периодическая проверка)

**Триггеры:**
- Каждые `AGENT_CRITIC_INTERVAL` шагов (по умолчанию 5)
- При блокировке плана

**Алгоритм:**

```
1. Наступление интервала проверки (stepCount % CriticInterval == 0)
   ↓
2. Наблюдение текущего состояния страницы (Observe)
   ↓
3. Сбор контекста:
   - Цель задачи
   - Текущий план (шаги, текущий шаг, блокировки)
   - История последних 10 шагов
   - Текущее состояние страницы (URL, title, overlays)
   ↓
4. LLM-анализ (Critic.Critique):
   - Оценка прогресса (0.0 - 1.0)
   - Определение on_track (true/false)
   - Выявление проблем (issues)
   - Рекомендации (recommendations)
   - Определение блокировки (blocked, block_reason)
   ↓
5. Обработка результатов:
   - Если blocked = true: план помечается как заблокированный
   - Если issues найдены: добавляются в блокеры памяти
   - Рекомендации логируются для анализа
```

**Пример сценария:**

```
Шаг 5 из 10: Critic проверка
Контекст: 
  - Задача: "Найти товар на Ozon"
  - История: navigate → observe → type → click → observe
  - Текущее состояние: Страница результатов поиска
Critic анализ:
  - progress: 0.5
  - on_track: true
  - issues: []
  - recommendations: ["Проверить фильтры для уточнения поиска"]
Результат: План продолжается без изменений
```

### Уровень 3: Error Recovery (при ошибках)

**Триггеры:**
- Ошибка выполнения шага
- Превышение лимита попыток на шаг

**Алгоритм:**

```
1. Ошибка выполнения шага
   ↓
2. Увеличение счётчика попыток (currentStepRetries++)
   ↓
3. Если попыток < maxRetries:
   → Вызов recoverFromError:
      a. Наблюдение текущего состояния
      b. Вызов Planner.UpdatePlan с описанием ошибки
      c. Обновление плана
      d. Сброс счётчика попыток (если шаг изменился)
   → Повторная попытка выполнения
   ↓
4. Если попыток >= maxRetries:
   → Rollback на предыдущий шаг
   → Если rollback успешен: continue
   → Если rollback неудачен: recoverFromError → новый план
```

**Пример сценария:**

```
Шаг: "Найти кнопку 'Добавить в корзину'"
Ошибка: Элемент не найден (после 3 попыток)
Recovery:
  1. Observe текущего состояния
  2. Planner.UpdatePlan: "Элемент 'Добавить в корзину' не найден. Возможно, товар уже в корзине или страница изменилась"
  3. Новый план: "Проверить состояние корзины → Если товар не в корзине, найти альтернативную кнопку"
  4. Продолжение с обновлённым планом
```

### Обновление плана

**Planner.UpdatePlan** вызывается в следующих случаях:

1. **Progress Check обнаружил отклонение:**
   - Контекст: описание выполненного шага, фактический результат, следующий шаг
   - Результат: план обновлён с учётом фактического состояния

2. **Error Recovery при ошибке:**
   - Контекст: текущий план, состояние страницы, описание ошибки
   - Результат: план обновлён для обхода проблемы

3. **Critic обнаружил проблемы:**
   - Контекст: рекомендации Critic, текущее состояние
   - Результат: план может быть обновлён (если Critic явно рекомендует)

**Процесс обновления:**

```
1. Сбор контекста:
   - Текущий план (JSON)
   - Текущее состояние (URL, title)
   - Описание проблемы/отклонения
   ↓
2. LLM-анализ (Planner.UpdatePlan):
   - Анализ текущего плана
   - Понимание проблемы
   - Генерация обновлённого плана
   ↓
3. Парсинг нового плана:
   - Валидация JSON структуры
   - Проверка корректности шагов
   ↓
4. Применение обновления:
   - Замена текущего плана
   - Сброс счётчика попыток (если шаг изменился)
   - Продолжение выполнения
```

### Преимущества алгоритма

1. **Реактивность**: Быстрое обнаружение проблем через Progress Check
2. **Проактивность**: Предотвращение проблем через Critic Check
3. **Устойчивость**: Восстановление после ошибок через Recovery
4. **Адаптивность**: Динамическое обновление плана на основе реального состояния
5. **Эффективность**: Оптимизированные проверки (Progress Check только после важных действий, Critic Check периодически)

### Пример полного цикла

```
Задача: "Найти товар iPhone на Ozon и добавить в корзину"

Шаг 1: navigate → https://ozon.ru
  Progress Check: ✅ URL изменился, страница загружена

Шаг 2: type → "iPhone" в поле поиска
  Progress Check: ✅ Текст введён, поле видно

Шаг 3: click → кнопка "Найти"
  Progress Check: ❌ Страница не изменилась, возможно кнопка не нажата
  → Plan Update: Добавлен шаг "Проверить состояние поиска"

Шаг 4: observe → проверить результаты
  Progress Check: ✅ Результаты поиска отображаются

Шаг 5: click → первый товар
  Progress Check: ✅ Переход на страницу товара
  Critic Check: ✅ progress=0.6, on_track=true

Шаг 6: click → "Добавить в корзину"
  Progress Check: ❌ Кнопка не найдена (возможно товар уже в корзине)
```

## Конфигурация

### Основные параметры

`.env` файл содержит следующие настройки:

**OpenAI:**
- `OPENAI_API_KEY` - API ключ OpenAI
- `OPENAI_MODEL` - модель LLM (рекомендуется `gpt-4o-mini`)
- `OPENAI_TIMEOUT` - таймаут для LLM запросов (по умолчанию 5m)
- `OPENAI_MAX_RETRIES` - максимальное количество повторных попыток

**Browser:**
- `CHROME_PROFILE_DIR` - путь к профилю Chrome
- `BROWSER_TIMEOUT` - общий таймаут браузера
- `BROWSER_NAVIGATION_TIMEOUT` - таймаут для навигации
- `BROWSER_ACTION_TIMEOUT` - таймаут для click/type действий
- `BROWSER_VIEWPORT_WIDTH` - ширина viewport (по умолчанию 1920)
- `BROWSER_VIEWPORT_HEIGHT` - высота viewport (по умолчанию 1080)

**Agent:**
- `AGENT_MAX_STEPS` - максимальное количество шагов (по умолчанию 100)
- `AGENT_CRITIC_INTERVAL` - интервал проверки Critic (по умолчанию 5)
- `AGENT_EPHEMERAL_SIZE` - размер ephemeral памяти (по умолчанию 3)
- `AGENT_WORKING_SUMMARY_SIZE` - размер working summary (по умолчанию 1500)
- `AGENT_MAX_RETRIES` - максимальное количество повторных попыток на шаг (по умолчанию 3)
- `AGENT_DRY_RUN` - режим dry run (по умолчанию false)

**Logging:**
- `LOG_LEVEL` - уровень логирования (debug, info, warn, error)
- `LOG_FORMAT` - формат логов (json, console)
- `RUN_DIR` - директория для сохранения логов и скриншотов (по умолчанию ./runs)

## Механизмы восстановления и отказоустойчивости

### Retry механизм

- **Экспоненциальный backoff**: При ошибках LLM или браузера используется экспоненциальный backoff
- **Максимум попыток**: До `AGENT_MAX_RETRIES` попыток на каждый шаг
- **Сброс счетчика**: Счетчик попыток сбрасывается при успешном выполнении шага

### Rollback механизм

При превышении лимита попыток на шаг:
1. Агент откатывается на предыдущий шаг
2. План обновляется через Planner.UpdatePlan
3. Выполнение продолжается с предыдущего шага

### Recovery механизм

При критических ошибках:
1. Critic анализирует текущее состояние и историю
2. Planner создаёт новый план с учётом ошибок
3. Агент продолжает выполнение с обновлённым планом

### Fallback механизм

Для click/type действий:
1. **Vision-путь**: Скриншот → LLM анализ → DOM-валидация → ClickAt/TypeAt
2. **Fallback**: Если vision не находит элемент или валидация не проходит → selector-based поиск через Playwright locators
3. **Selector-based**: Использует role, name, placeholder, text_contains для поиска элемента

### Progress Check и адаптация плана

- **Условия**: После click/type/navigate, и после scroll (если следующий шаг - observe/click/type)
- **Процесс**: Скриншот → LLM анализ → определение прогресса
- **Адаптация**: Если прогресс не соответствует ожиданиям, план обновляется автоматически

## Производительность

### Время выполнения

Типичное время выполнения зависит от:
- **Сложности задачи**: Простые задачи (3-5 шагов) - 2-5 минут, сложные (10+ шагов) - 10-15 минут
- **Модели LLM**: `gpt-4o-mini` быстрее `gpt-4o`, но качество может быть немного ниже
- **Скорости интернета**: Vision-анализ требует передачи изображений в OpenAI API
- **Скорости загрузки страниц**: Зависит от сайта и интернет-соединения

### Оптимизация производительности

1. **Используйте gpt-4o-mini**: Быстрее и дешевле для большинства задач
2. **Уменьшите таймауты**: Для быстрых сайтов можно уменьшить `BROWSER_ACTION_TIMEOUT`
3. **Настройте Critic interval**: Для простых задач можно увеличить `AGENT_CRITIC_INTERVAL`
4. **Используйте dry run**: Для тестирования планов без реального выполнения

### Известные ограничения производительности

- Vision-анализ требует времени на передачу скриншота и получение ответа от LLM
- DOM-валидация выполняется через JavaScript в браузере, что может замедлять выполнение
- Progress check добавляет дополнительное время после каждого важного действия
